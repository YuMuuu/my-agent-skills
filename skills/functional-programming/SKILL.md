# Functional Programming

コード生成とコードレビューでは、対象言語の慣用性を尊重しながら関数型言語のエッセンスを適用する。関数型の形式を目的にせず、変更の局所化、推論しやすさ、テスト容易性を改善する設計を選ぶ。

## 基本原則

### 純粋関数

同じ入力に対して常に同じ出力を返し、外部状態を読んだり変更したりしない関数を優先する。純粋関数はテストしやすく、実行順序や並行実行の影響を受けにくい。

- グローバル状態、時刻、乱数、環境変数、I/O を計算ロジックから直接参照しない。
- 必要な値は引数として受け取り、結果は戻り値として返す。
- 状態変更が必要な場合は、変更する境界を小さく保つ。

### 参照透過性（透過参照）

式や関数呼び出しを、その評価結果で置き換えてもプログラムの意味が変わらない状態を目指す。呼び出し結果を予測できない処理は、純粋な計算と副作用のある処理に分ける。

### 不変データ

既存の値を変更するより、新しい値を生成する。共有された可変状態を減らし、エイリアスによる予期しない変更を防ぐ。

基本的にはイミュータブルに実装する。パフォーマンス上の理由でどうしてもミュータブルな実装が必要な場合は、実装前にユーザーへ確認し、採用理由と変更範囲をコードコメントに残す。ミュータブルな状態は可能な限り局所化し、外部へ漏らさない。

- コレクションを走査中に変更しない。
- 状態遷移は、旧状態から新状態を返す関数として表現する。
- 言語が提供する immutable な型や persistent data structure を優先する。

### 全域関数

入力の定義域にあるすべての値に対して結果を返す全域関数を優先する。想定外の入力で例外を投げたり、未定義値を返したりする部分関数を避ける。

- 配列の直接 index 参照より、`Option`、`Maybe`、安全な検索関数を使う。
- `Result`、`Either`、専用のエラー型などの言語機能が利用できる場合は、失敗を戻り値のデータとして扱う。
- 空のコレクション、境界値、異常系を仕様として扱う。

条件分岐にパターンマッチングや同等の機能がある場合は、入力のケースを明示し、網羅性を確認する。コンパイラーの網羅性検査がない言語では、default 分岐やテストで処理漏れを補う。

### 型で不正な状態を表現しない

型のある言語では、できるだけ型が表現できる値の範囲を狭め、実行時にしか分からない制約を減らす。単なる`String`ではなく`NonEmptyString`、`EmailAddress`、`UserId`などの意味を持つ型を使い、生成時に不変条件を検証する。

- 取り得る値が有限なら、文字列や数値ではなく enum、union、sealed type などで表現する。
- 正の数、範囲内の数、空でないコレクションなどは制約付きの型で表現する。
- 存在しない可能性は nullable な値で隠さず、`Option`、`Maybe`などで明示する。
- 失敗の種類を表現する機能がある言語では、例外や文字列ではなく`Result`、`Either`、専用の error type で表現する。
- 型変換や検証は境界で一度だけ行い、検証済みの値を内部ロジックへ渡す。

ADT（代数的データ型）を利用できる言語では、データの組み合わせを product type、選択肢を sum type として表現する。状態と状態遷移を ADT にまとめ、許可されない状態や処理ケースを型とパターンマッチングで減らす。

## コレクション操作

### 畳み込み

コレクションから結果を組み立てる処理では、畳み込み関数を優先する。
手作業の mutable な accumulator より`foldLeft`、`fold`、`reduce`などを使う。
初期値を明示し、空のコレクションでも定義できる場合は`foldLeft`を選ぶ。

```text
foldLeft(initial, combine, items)
```

`map`、`filter`、`flatMap`、`groupBy`など、目的を直接表すコレクション操作を優先する。処理の目的を記述する宣言的な表現にし、単なる変換を副作用付きの loop で実装しない。

ただし、速度またはメモリ使用量が要件を満たさない場合は、対象言語の iterator や stream を使う。変更後に速度とメモリ使用量を測定する。

## 過剰適用を避ける

関数型の原則は、すべてのコードに同じ強さで適用しない。単純な script、短い変換処理、使い捨ての開発用コードでは、処理の流れが明確になるなら命令型の loop や局所的な mutable 変数を許容する。

- 数行の処理を無理に複数の抽象化へ分解しない。
- 小さな script では、純粋関数や effect 型を導入するために構造を複雑にしない。
- 共有状態や外部副作用がなく、読みやすさが保たれる局所的な変更は許容する。
- 長期保守する library、複雑なドメインロジック、並行処理、再利用されるコードでは原則を強く適用する。
- 採用しない原則がある場合も、可読性、テスト容易性、性能の観点から理由を説明できるようにする。

## 副作用の分離

副作用を消す必要はない。制御しやすい境界に集約する。
ドメインロジックを純粋な計算として実装する。
I/O、ログ、DB、ネットワーク、時刻、乱数などは外側の薄い層で扱う。

```text
入力を読む → 純粋な操作で判断する → コマンドとして結果を適用する
```

依存性はグローバルに隠さず、引数、インターフェース、context、effect 型などで明示する。これにより、テストでは副作用を stub や fake に置き換えられる。

純粋な操作を副作用から分離し、I/O や外部サービスなしで単体テストできる構造にする。副作用を持つ境界は少数の結合テストで確認し、ドメインロジックの大部分は高速な単体テストで検証する。

## コマンドと操作の分離

「何をするか」を表す操作と、「実際に実行する」コマンドを分離する。操作は入力から結果または実行計画を返し、コマンドはその計画を I/O や外部システムに適用する。

- 操作は純粋関数としてテストする。
- コマンドは副作用の実行とエラー処理に集中させる。
- 操作の戻り値に、更新内容や実行すべき副作用をデータとして表現する方法も検討する。
- コマンドからドメインルールを直接計算しない。

## コード生成時の手順

1. 入力、出力、失敗条件、副作用を明確にする。
2. 純粋な操作と副作用を実行するコマンドを分ける。
3. 可変状態、null、例外、部分関数を減らす型とデータ構造を選ぶ。
4. コレクション処理は`map`、`filter`、`flatMap`、`foldLeft`などで意図を表現する。
5. 境界条件と失敗を含むテストを純粋な操作から作る。
6. 言語の性能特性とチームの可読性を確認し、過度に抽象化しない。

## コードレビューの観点

- 同じ入力でも結果が変化する関数を探す。
- 関数が外部状態を暗黙に読み書きしていないか。
- 入力全体に対して結果が定義されているか。
- null、例外、直接 index 参照などの部分関数が残っていないか。
- loop 内の mutable な accumulator を畳み込み関数に置き換えられないか。
- 実装・test・I/O が 1 つの関数やクラスに混在していないか。
- コマンドと操作が分離され、操作を副作用なしでテストできるか。
- 関数型の抽象化が、対象言語の慣用性や可読性を損なっていないか。
