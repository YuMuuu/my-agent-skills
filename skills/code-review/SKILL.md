# Code Review

コード生成とコードレビューを、実装前、実装中、実装後の 3 段階で確認する。一般原則と言語・ライブラリ固有の規約を区別し、対象コードに関係する規約だけを適用する。

レビューだけを依頼された場合は、コードを変更しない。問題の原因と影響を確認し、重要度の高い指摘から報告する。修正も依頼された場合は、指摘した問題を修正してから再度レビューする。

## 技術別リファレンス

対象プロジェクトで利用している技術だけを読む。

- Scala コードを生成またはレビューする場合は、[Scala](references/scala.md)を読む。
- Cats または Cats Effect を利用する場合は、[Cats](references/cats.md)も読む。
- Doobie を利用する場合は、[Doobie](references/doobie.md)も読む。
- Actor を利用する場合は、[Pekko Typed Actor hierarchy](references/actor-hierarchy.md)も読む。
- SLF4J、MDC または非同期ログコンテキストを扱う場合は、[JVM logging](references/jvm-logging.md)も読む。

コメントの追加やレビューが依頼範囲に含まれる場合は、利用可能なら`code-comments` skill を併用する。この skill ではコメント規約を重複して定義しない。

## 1. コード生成前

最初に対象コード、周辺コード、build 設定、既存の規約を調べる。リポジトリから判断できることをユーザーへ聞き直さない。

レイヤー構成には、各レイヤーの責務と許可される依存関係を含める。依存方向を別の設計項目として重複確認しない。

### 既存プロジェクト

次を確認し、既存の決定へ従う。

- アーキテクチャ、レイヤー構成と責務
- 言語と主要ライブラリのバージョン
- 設定管理、DI、DB アクセス、非同期処理の方式
- boot と shutdown の構成

方針が見つからない、一貫していない、または今回の変更で新しい方式を導入する必要がある場合だけ、実装前にユーザーへ確認する。

### プロジェクト最初の実装

アーキテクチャが指定されていない場合は、コードを書く前にユーザーへ確認する。あわせて、今回必要になる次の選択を確認する。

- レイヤー構成と責務
- DI を利用するか。利用する場合はどのライブラリか
- DB アクセスを行う場合はどのライブラリか
- 非同期処理または並行処理を扱う方式
- server、daemon、consumer などの boot 責務

一度決定したプロジェクト方針は、実装のたびに聞き直さない。

### 今回の変更

次を明確にする。

- 変更対象と変更しない範囲
- 実装するレイヤーと呼び出し方向
- 入力、出力、成功条件、失敗条件
- 新しく登場するドメイン概念と不変条件
- DB、network、filesystem、logging などの副作用
- 起動、終了、並行実行、キャンセルへの影響

## 2. コード生成中の最小チェック

実装中は、後から直すと設計変更になりやすい事項を優先して確認する。

- レイヤー構成と責務を維持する。
- ドメインロジックを I/O や framework の都合から分離する。
- ドメイン上の異なる概念を同じプリミティブ型で表現しない。
- 想定可能な失敗を、分類可能なエラー型で表現する。
- 公開境界へ内部合成用の型や infrastructure 固有の型を漏らさない。
- resource の生成者、所有者、解放責務を明確にする。
- boot、shutdown、非同期処理を変更する場合は、処理全体のライフサイクルを確認する。
- 対象技術のリファレンスにある生成中の規約を適用する。

## 3. コード生成後のレビュー

生成・変更した差分だけでなく、関連する型、呼び出し元、設定、test も確認する。

### 一般的な確認

- 要求された振る舞いと失敗条件を満たしているか。
- レイヤー構成、責務、公開 interface を壊していないか。
- ドメイン概念、不変条件、境界値が型と validation で表現されているか。
- 想定可能なエラーと予期しない障害を混同していないか。
- エラーを握り潰したり、ログだけを出して成功扱いにしたりしていないか。
- エラーログに trace ID、request ID、entity ID、job ID など、障害調査に必要な ID があるか。
- password、token、個人情報などをログへ出していないか。
- resource leak、停止不能、重複起動、非協調的なキャンセルがないか。
- server の中で無関係な daemon を boot するなど、起動責務が混在していないか。
- 変更で不要または不正確になった test、設定、文書が残っていないか。

### 検証

変更量と危険度に応じて、formatter、linter、compile、test を実行する。実行できない検証がある場合は、その理由と未確認の範囲を報告する。警告を無視せず、今回の変更が原因かを確認する。

### レビュー結果

指摘には、対象箇所、問題、発生条件または影響、修正方針を含める。スタイル上の好みではなく、正しさ、障害調査性、保守性、既存規約との整合性に基づいて指摘する。

問題がない場合も、実行できなかった test や確認できない運用条件など、残るリスクがあれば明示する。

## 一般的な設計規約

### ドメイン型

ドメイン上の異なる概念を同一のプリミティブ型で表現しない。ID、名称、時刻、金額、数量、ステータス、外部識別子などが対象になる。対象言語の newtype、opaque type、value object、record、enum、tagged union などを使って区別する。

- 値の生成時に不変条件を検証する。
- HTTP、DB、設定、message などの境界で変換し、内部ではドメイン型を維持する。
- 異なる ID、単位、通貨、時刻基準を誤って入れ替えられない型にする。
- 有限の状態集合は文字列や数値ではなく、網羅性を検査できる型で表現する。

### 非同期interface境界

非同期処理を扱う境界では、非同期実行と想定可能な失敗を型で区別する。対象言語が提供する非同期型と、`Result`や error union などの失敗表現を利用する。

純粋なドメイン処理を、I/O 都合の非同期型へ依存させない。内部処理を合成するための型は、外部 interface へ露出させない。

### bootとshutdown

- application 全体を組み立てる boot 層と、個別の処理を担う層を分ける。
- resource を取得した scope で解放方法も定義する。
- 新規受付の停止、実行中処理の完了待機、resource 解放の順序を設計する。
- shutdown を冪等にし、timeout 時の動作を定義する。
- 長時間処理は停止要求を観測する。要求を受けたら cooperative shutdown を開始する。
