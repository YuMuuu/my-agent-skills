# Code Comments

コード内コメントを書くときは、読み手がコードだけでは知り得ない情報を残す。基本的な対象は「何をしているか」ではなく「なぜそうしているか」であり、コメントを書く前にコード自体で意図を表現できないかを確認する。

## 基本方針

- コメントは、コードから表現できない意図、理由、制約、前提、設計上の判断を説明する。
- コメントは、将来の変更で壊されやすい意図や、見た目に反して必要な実装である理由を保護するためにも使う。
- コメントは日本語で書く。文体は簡潔で、読み手にとって自然な表現にする。
- 短く具体的に書き、コードと同じ情報を繰り返さない。
- 正規表現、複雑なアルゴリズム、処理順序など、処理内容そのものがコードから読み取りにくい場合は、処理内容（what）の説明も許容する。
- クラス、モジュール、関数の目的・使い方・振る舞いを説明する文書コメントは、行コメントとは区別して書く。

## ドメインコードの文書コメント

ドメインコードには、業務上の定義と仕様を文書コメントとして記述する。ドメイン型、ドメインサービス、状態遷移、業務ルールが対象になる。実装の言い換えではなく、次の情報から必要なものを選ぶ。

- ドメイン用語が業務上何を意味するか
- 値や状態が成立する条件と不変条件
- 境界値、単位、時刻基準、丸めなどの規則
- 許可または禁止される状態遷移
- 類似する別のドメイン概念との違い

型名や validation から明らかな内容は繰り返さない。業務仕様を確認できない場合は推測でコメントを書かず、ユーザまたは既存の仕様へ確認する。

```scala
/**
 * 顧客が1回の注文で指定する商品の数量。
 */
opaque type OrderQuantity = Int
```

## コメントの種類

### 通常コメント

通常コメントには、コードだけでは分からない情報を書く。対象は、コードが必要な理由、設計上の理由、制約、前提、将来変更すると壊れる不変条件などである。処理内容を単に言い換えるだけなら書かない。

```ts
// 外部サービスのレート制限を避けるため、ここでは一度だけ取得して再利用する。
const config = fetchConfig();
```

### TODOコメント

TODO コメントには、後で対応が必要な事項を書く。対象は、将来の改善、未実装の機能、検討すべき変更、確認したい課題などである。現時点では残してよいものに限る。対応内容を具体的にし、可能なら関連する issue やチケットを添える。

```ts
// TODO: ページング対応後に全件取得を廃止する（Issue #123）。
const users = fetchAllUsers();
```

### FIXMEコメント

既知の不具合、危険な実装、早急に修正すべき問題を書く。問題の内容と影響を具体的にし、可能なら再現条件や関連する issue を添える。新しい問題を隠すためや、理由のない一時的なラベルとして使わない。

```ts
// FIXME: タイムアウト時に接続が解放されず、リクエスト数が増えるとリークする。
sendRequestWithoutCleanup();
```

TODO と FIXME は対応漏れを防ぐための追跡対象である。対象言語の標準的なコメント構文で書き、曖昧な説明にせず、何を、どの条件で対応するかが分かる文章にする。

## ワークフロー

1. 対象コードと周辺の文脈を読む。関数全体、関連する型・定数・呼び出し元、既存の通常コメント、TODO、FIXME も確認する。
2. コメントで伝えるべき情報を分類する。
   - 意図・理由: なぜこの実装や順序を選んだか
   - 制約・前提: 外部 API、スレッド安全性、互換性、性能、データ形式など
   - 将来の注意: 変更すると壊れる不変条件や、意図的な例外
   - 処理の説明: コードだけでは理解しにくい正規表現・アルゴリズムなど
3. その情報が、変数名の改善、処理の分割、メソッド抽出、明示的なチェックなどによってコード自体に表現できないか確認する。
4. 次の分岐で対応を決める。
   - コードがすでに明確で、候補のコメントが処理内容（what）を繰り返すだけの場合: コメントを書かない。コード改善の提案も不要である。
   - コードが不明瞭で、改善すれば処理内容（what）のコメントが不要または短くなる場合: コードを変更する前に、具体的な改善案を示してユーザへ確認する。
   - コードから分からない理由・制約・前提がある場合: 通常コメントを書く。
   - 正規表現や複雑なアルゴリズムなど、コードだけで処理を明確に表現するのが難しい場合: 必要最小限の処理内容（what）のコメントを書く。
5. コード改善を提案した場合は、ユーザの回答に従う。
   - 承認された場合: 必要な範囲だけコードを改善し、改善後にコメントが必要か再判断する。
   - 承認されなかった場合: コードを変更せず、処理内容（what）を繰り返すだけのコメントも追加しない。コードから分からない理由や制約がある場合だけコメントを書く。
   - ユーザが最初からコードを変更しないよう指定している場合: 改善の確認を省略し、コードを変更しない。処理内容（what）を繰り返すだけのコメントは追加しない。
   - 回答がない場合: コードを改善せず、確認待ちとして止める。
6. 内容に応じて通常コメント、TODO、FIXME を選ぶ。
7. コメントを書いた後、コードの処理を逐語的に繰り返していないか、将来も正しい内容か、既存コメントと矛盾しないか確認する。
8. 変更を依頼された場合は、コメント以外のコードを変更したかどうかを明示する。依頼されていないリファクタリングや TODO の削除は行わない。

## コメントを書かない例

次のようなコメントは、通常は書かない。

```ts
// ユーザーをすべて取得する
const users = userService.getAllUsers();

// 名前が空か確認する
if (name.isEmpty()) {
  // ...
}
```

この例ではコード自体が明確なので、コメントを追加せず、コード改善の確認も行わない。コードが不明瞭で、改善によってコメントが不要になる場合だけユーザへ確認する。

## コメントを書く例

```ts
// キャッシュの更新中に別スレッドから古い値を読まないよう、ここではロックを保持する。
refreshCacheWhileLocked();
```

```ts
// この順序を変えると、外部サービスが発行したトークンを検証する前に保存してしまう。
validateToken(token);
saveSession(token);
```

## 確認メッセージの例

たとえば、次の計算式にコメントを求められたが、式の意図がコードから分かりにくい場合を考える。

```ts
const total = price * quantity + tax;
```

`// 合計金額を計算する`では処理内容（what）の繰り返しになるため、次のように確認する。

> この式にコメントを付けても、処理内容の繰り返しになります。計算処理を`calculateTotal`として抽出し、コード自体から意図が分かるようにしてよいですか？ 承認されない場合はコードを変更せず、ノイズになるコメントも追加しません。

## 最終チェック

- コメントはコードから読み取れない情報を伝えているか
- 「なぜ」を説明しているか
- コードの処理を単に言い換えていないか
- コードを改善する場合、実施前にユーザへ確認したか
- コメントは現在の実装と一致し、将来も陳腐化しにくいか
- ドメインコードに必要な業務上の定義、仕様、不変条件が記述されているか
- 既存の TODO やコメントを確認したか
- 変更で不要になったコメントを特定したか
- 通常コメント・TODO・FIXME の種類を、内容に応じて適切に選んだか
- TODO/FIXME に具体的な対応内容や関連情報を記載したか
